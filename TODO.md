# ITSM-бот: очередь заявок в Telegram

Источник истины по продукту. Код следует за этим файлом, не наоборот.

---

## 1. Задача

Сейчас сотрудники пишут о проблемах в личку одному человеку. Системы заявок нет.
Обращения не теряются, но у процесса нет ни очереди, ни статусов, ни истории:
нельзя сказать, сколько их было за месяц, сколько они ждут и что ломается чаще.

Бот выносит обращения из личной переписки в очередь с номерами и статусами.

**Чем меряем, что получилось** — запрос к БД через месяц работы:

| Показатель | Как считается | Целевое значение |
|---|---|---|
| Доля обращений через бота | заявки в БД / (заявки в БД + обращения в личку) | > 80% |
| Заявки без ручного уточнения кабинета | `room_snapshot IS NOT NULL` при создании | > 95% |
| Заявок на одно обращение | заявки / сообщения от заявителей | ≈ 1.0 (склейка работает, см. F5) |
| Закрытые заявки | `status = 'done'` / все | > 90% |
| Среднее время до взятия в работу | `avg(taken_at - created_at)` | базовая линия, цели нет |

**Вне задачи:** маршрутизация между исполнителями, SLA и эскалации, интеграция с
GLPI/Jira, база знаний, классификация обращений, автоответы. Основания — раздел 4.

## 2. Требования

### 2.1 Функциональные

| # | Требование | Проверка приёмки |
|---|---|---|
| F1 | Первое обращение незнакомого сотрудника запускает сбор профиля: кабинет, отдел | новый `telegram_id` → строка в `employees` с заполненными `room` и `department` |
| F2 | Профиль спрашивается один раз; дальше подставляется сам | второе обращение того же человека не задаёт вопросов |
| F3 | Сотрудник правит профиль командой `/profile` | `employees.room` изменился, `updated_at` обновился |
| F4 | Обращение попадает в БД и в закрытую группу очереди одним сообщением | `tickets` +1 строка, в группе сообщение с номером |
| F5 | Подряд идущие сообщения одного человека склеиваются в одну заявку | три сообщения за 30 с → одна строка в `tickets` с тремя строками текста |
| F6 | Кнопки в группе меняют статус: `new` → `in_progress` → `done` | нажатие меняет `tickets.status` и текст той же карточки, новых сообщений в группе не появляется |
| F7 | Смена статуса уведомляет заявителя в его чат | после `done` заявителю ушло сообщение с номером заявки |
| F8 | Исполнитель отвечает reply на карточку — вопрос уходит заявителю, ответ привязывается к заявке | в `ticket_messages` две строки с нужными `direction`; второй вопрос тому же сотруднику до ответа отклонён |
| F9 | `/my` показывает сотруднику его открытые заявки | список совпадает с выборкой по `requester_id` и `status NOT IN ('done', 'cancelled')` |
| F10 | Секреты и ПДн маскируются до записи в БД | тест: сообщение с паролем → в `tickets.text` плейсхолдер, оригинала нет нигде |
| F11 | `/stats` отдаёт исполнителю сводку за период | число заявок, среднее время до закрытия, топ заявителей |

### 2.2 Нефункциональные

| # | Требование | Значение |
|---|---|---|
| N1 | Сотрудников в контуре | 50–200 |
| N2 | Обращений в рабочий день | до 5 (~1200 в год) |
| N3 | Окно склейки сообщений в одну заявку (F5) | 45 с после последнего сообщения |
| N4 | Время от закрытия окна склейки до появления в группе очереди | < 3 с |
| N5 | Перезапуск процесса не теряет **созданные** заявки | состояние в БД; в памяти живёт только недособранный буфер склейки — основание D13 |
| N6 | Хранилище | SQLite, файл на диске ВМ |
| N7 | Бэкап БД | ежедневная копия файла, хранить 30 дней |
| N8 | Сырой текст обращения нигде не сохраняется | ни в БД, ни в логах, ни в группе очереди |
| N9 | Секреты бота | переменные окружения, `.env` вне репозитория |
| N10 | Рейт-лимит на сотрудника | 5 заявок в час |
| N11 | Дедупликация | одинаковый текст от одного человека за 10 мин не заводит вторую заявку |
| N12 | Длина текста в карточке очереди | 1200 символов, дальше `…` и подсказка `/ticket <номер>`; в БД лежит полный текст |

При N2 = 5 в день объём за год — порядка 1200 строк. Это определяет почти всё
остальное: SQLite без вариантов, очередь помещается в один экран, ручные операции
исполнителя не успевают стать нагрузкой.

## 3. Модель данных

```
employees
  telegram_id         TEXT PK        -- id Telegram, не меняется
  display_name        TEXT           -- из Telegram-метаданных
  room                TEXT           -- кабинет, спрашивается один раз
  department          TEXT           -- значение из справочника (D10)
  language            TEXT           -- ru | en, язык ответов бота (D14)
  created_at          TIMESTAMP
  updated_at          TIMESTAMP

tickets
  id                  INTEGER PK     -- номер, который видит человек: «#47»
  requester_id        TEXT FK employees.telegram_id
  text                TEXT           -- замаскированный текст, склеенный из сообщений
  status              TEXT           -- new | in_progress | done | cancelled
  room_snapshot       TEXT           -- кабинет на момент заявки
  department_snapshot TEXT
  security_flag       BOOLEAN
  source_chat_id      INTEGER        -- куда отвечать заявителю
  source_message_id   INTEGER        -- первое сообщение пачки
  queue_message_id    INTEGER NULL   -- карточка в группе: правка кнопок и привязка F8
  text_hash           TEXT           -- для дедупликации (N11)
  created_at          TIMESTAMP
  taken_at            TIMESTAMP NULL
  closed_at           TIMESTAMP NULL

ticket_messages                      -- переписка по заявке
  id                  INTEGER PK
  ticket_id           INTEGER FK tickets.id
  direction           TEXT           -- to_requester | from_requester
  text                TEXT           -- замаскированный
  created_at          TIMESTAMP
```

**Почему `room_snapshot`, а не только `employees.room`.** Люди переезжают. Заявка
годичной давности должна помнить кабинет, в который тогда ходили, иначе отчёт по
локациям врёт задним числом.

**Почему номер заявки — автоинкремент, а не UUID.** Номер называют вслух и пишут в
переписке: «что там с 47-й». UUID для этого непригоден.

**Почему язык хранится в профиле, а не берётся из сообщения.** Уведомление о смене
статуса (F7) отправляется в ответ на действие исполнителя, а не заявителя, и
`language_code` заявителя в этом апдейте недоступен. Язык — такое же свойство
человека, как кабинет (D2), и хранится там же.

**Полей `category` и `priority` нет.** Основание — D3.

## 4. Решения и основания

Решение записано с причиной и с условием пересмотра. Без условия пересмотра решение
превращается в догму.

| # | Решение | Почему | Пересмотреть, если |
|---|---|---|---|
| D1 | Без LLM | классификация нужна для маршрутизации между исполнителями — исполнитель один; кабинет и отдел дешевле спросить один раз, чем извлекать из каждого текста. При 5 заявках в день (N2) никакая автоматизация разбора не окупается | поток вырастет до 50+ в день **и** появятся исполнители, между которыми надо распределять |
| D2 | Профиль сотрудника вместо извлечения локации из текста | кабинет не меняется от заявки к заявке — это свойство человека, а не сообщения | сотрудники перестанут быть привязаны к кабинетам |
| D3 | Категория и приоритет не хранятся вовсе | при одном исполнителе и 5 заявках в день приоритет виден глазами, а категория нужна только для отчёта, которого никто не просит | владельцу понадобится отчёт по типам проблем |
| D4 | SQLite, файл на диске | ~1200 строк в год, один процесс на запись | > 1000 сотрудников или второй пишущий процесс |
| D5 | Маскирование остаётся при любой архитектуре | пароли присылают независимо от того, есть в системе модель или нет | никогда |
| D6 | Сырой текст не сохраняется | главное требование ИБ; отдельного хранилища оригиналов нет по замыслу | явное решение владельца с описанием контроля доступа и TTL |
| D7 | Склейка сообщений по таймеру, а не кнопка «Отправить» | в личку пишут очередями: «Здравствуйте» → «принтер» → «не печатает». Кнопка требует от человека изменить привычку, таймер — нет | окажется, что люди пишут одним сообщением и таймер только добавляет задержку |
| D8 | Статусы: 4 значения | `new`, `in_progress`, `done`, `cancelled` покрывают процесс из одного исполнителя | появится второй исполнитель — понадобится `assigned` и поле исполнителя |
| D9 | Очередь в закрытой Telegram-**группе**, не в вебе | ноль инфраструктуры, работает с телефона, уведомления уже есть. Группа, а не канал: посты канала бот-администратор получает, но в канале нет личности автора — пост админа публикуется от имени канала, `from_user` отсутствует, `ForceReply` не поддерживается, и связать набранный исполнителем текст с конкретной заявкой нечем. В группе исполнитель отвечает reply на карточку, и `reply_to_message.message_id` совпадает с `queue_message_id` — привязка вопроса к заявке без состояния в памяти и без миграции | понадобится доступ нескольким людям с разными правами |
| D10 | Отдел выбирается кнопками из справочника в конфиге, свободного ввода нет | при N1 = 50–200 свободный ввод даст «ИТ», «IT», «айти» в одной колонке, и показатель по отделам станет нечитаемым. Справочник правится реже, чем раз в квартал | оргструктура начнёт меняться чаще, чем справочник успевают править, или понадобится отдел вне списка |
| D11 | `cancelled` ставит только исполнитель | заявок 5 в день (N2), лишний клик исполнителя не нагрузка, а проверка прав в колбэках сотрудника — код, который нечем оправдать. Передумавший сотрудник пишет об этом, исполнитель нажимает | на пилоте окажется, что ошибочных заявок заметная доля и исполнитель тратит на них время |
| D12 | Сообщение по уже закрытой заявке заводит новую, переоткрытия нет | сообщение вне контекста открытой заявки — новое обращение. Переоткрытие ломает показатель «среднее время до закрытия»: заявка закрывается дважды, а история переоткрытий нигде не хранится | на пилоте люди будут систематически дописывать к закрытым заявкам вместо новых обращений |
| D13 | Буфер склейки живёт в памяти процесса, не в БД | в буфере лежит сырой текст, а он не должен касаться диска (D6, N8). Маскировать до склейки нельзя: `redact()` работает по контексту, и «пароль» в одном сообщении со значением в следующем распознаётся только на склеенном тексте. N5 читается как «созданные заявки не теряются»: перезапуск теряет только необработанное обращение — несобранную пачку и пачку, ждущую уточнения, к какой заявке она относится | появится требование переживать перезапуск без потери недособранного обращения, и найдётся способ не класть сырой текст на диск |
| D14 | Язык ответа хранится в `employees.language` | `language_code` доступен только в апдейте от самого заявителя, а уведомления (F7) отправляются по действию исполнителя | ответы станут только на одном языке |
| D15 | Ответ заявителя привязывается по состоянию «заявка ждёт ответа», а не по reply; решение принимается **один раз на склеенную пачку**; неотвеченный вопрос у сотрудника в каждый момент **ровно один** | reply на телефоне делают не все, и требование его ставить превратит часть ответов в мусорные заявки без контекста. Состояние выводится запросом (заявка не закрыта, последняя реплика — `to_requester`), новых колонок не нужно. Решать на каждом сообщении нельзя: на вопрос «какая модель и какая ошибка» отвечают двумя сообщениями, первое сняло бы признак ожидания, и второе уехало бы в новую заявку — ровно тот сценарий, ради которого существует D7. Второй вопрос тому же человеку бот не даёт задать, пока первый без ответа: иначе сообщение сотрудника двусмысленно, и приходится спрашивать кнопками «к какой заявке», а это отложенное хранение сырого текста со своим жизненным циклом. При одном исполнителе и 5 заявках в день (N2) дешевле дождаться ответа или задать всё одним сообщением | исполнителю начнёт систематически не хватать одного открытого вопроса на сотрудника |

## 5. Безопасность

- Весь текст проходит `redact()` **до** записи в БД, до отправки в группу и до логов.
  Поток односторонний и необратимый (D6).
- `security_flag: true` → заявка создаётся, сотруднику приходит предупреждение не
  присылать пароли. Заявка не отклоняется.
- Токен бота, id группы очереди и путь к БД — переменные окружения, `.env` в `.gitignore`.
- Файл БД лежит на ВМ в контуре компании, наружу не выставляется.
- Логи пишутся через `logging`, содержат номер заявки и `telegram_id`, но не текст
  обращения.

### Этап 2 — бот

Границы модулей проведены по тестируемости: `buffer.py`, `intake.py`, `routing.py`,
`cards.py` не знают про типы aiogram и проверяются обычным pytest без моков.
Хендлеры остаются переходниками на десяток строк — их проверяет ручной прогон
F1–F11. Отдельной зависимости для тестирования aiogram не вводится.

```
src/itsm_bot/bot/
  main.py          сборка Dispatcher, polling, корректное завершение
  middlewares.py   сессия БД в data хендлера
  buffer.py        склейка сообщений и блокировка на telegram_id (D13)
  intake.py        единственная точка создания заявки
  routing.py       правило «ответ по заявке или новое обращение» (D15)
  cards.py         тексты и клавиатуры, RU/EN по employees.language (D14)
  handlers/        profile.py, messages.py, queue.py, commands.py
```

- [ ] Подготовка вне `bot/`: `departments` в `config.py` (обязательный список,
      парсится из строки через запятую — JSON в `.env` неудобен), колонка
      `employees.language` и миграция, выборки `/stats` и
      `tickets_awaiting_answer` в `repo.py`
- [ ] `buffer.py`: окно N3, реестр `asyncio.Lock` на `telegram_id`
- [ ] `intake.py`: под блокировкой — проверка дубля (N11), рейт-лимит (N10),
      `repo.create_ticket`, карточка в группу (F4, F10). `redact()` хендлер
      **не вызывает** — маскирование внутри слоя хранения, и второй вызов
      снаружи только сбил бы `security_flag`
- [ ] FSM сбора профиля при первом обращении: кабинет свободным вводом, отдел
      кнопками (F1, F2, D10). Первое обращение ждёт в буфере и уходит в заявку
      сразу после сохранения профиля
- [ ] `routing.py`: решение принимается на собранной пачке, внутри `intake` под той
      же блокировкой — ответ по ждущей заявке либо новая заявка. Хендлер сообщений
      только кладёт текст в буфер
- [ ] Callback-кнопки статусов, перерисовка той же карточки, уведомление
      заявителя (F6, F7); `cancelled` доступен только в группе (D11)
- [ ] Reply исполнителя на карточку → вопрос заявителю, привязка по
      `queue_message_id` (F8)
- [ ] `/my`, `/profile` (F3, F9); `/stats`, `/ticket <номер>` — только внутри
      группы очереди (F11, N12)
- [ ] Проверка автоматическая: склейка трёх сообщений в одну заявку, изоляция
      буферов разных сотрудников, гонка (см. ниже), все четыре ветки
      маршрутизации, выборки `/stats`. Тесты на гонку и на маршрутизацию
      проверяются мутацией
- [ ] Проверка ручная: каждое требование F1–F11 отмечено на живом боте

**Гонка при создании заявки.** `find_recent_duplicate` и `count_recent_tickets` —
отдельные чтения, а `create_ticket` коммитит сам по себе. Две параллельные обработки
могут обе не увидеть дубля и обе вставить заявку, либо обе насчитать 4 заявки и
превысить лимит в 5. Слой хранения это не лечит: атомарной он может стать только
зная, как устроен вызывающий. Требование к этапу 2: создание заявки для одного
сотрудника должно быть сериализовано — буфер склейки (F5) обязан быть единственной
точкой создания, с блокировкой на `telegram_id`. Проверка: два одновременных
обращения от одного человека с одинаковым текстом дают одну заявку.

Блокировка именно на сотруднике, а не глобальная: обращения из разных отделов
обрабатываются параллельно, а гонка возможна только между двумя обработками одного
человека. `asyncio.Lock` достаточен ровно потому, что пишущий процесс один (D4) —
это то же условие пересмотра, что уже записано у D4.
