# ITSM-бот: очередь заявок в Telegram

Источник истины по продукту. Код следует за этим файлом, не наоборот.

---

## 1. Задача

Сейчас сотрудники пишут о проблемах в личку одному человеку. Системы заявок нет.
Обращения не теряются, но у процесса нет ни очереди, ни статусов, ни истории:
нельзя сказать, сколько их было за месяц, сколько они ждут и что ломается чаще.

Бот выносит обращения из личной переписки в очередь с номерами и статусами.

**Чем меряем, что получилось** — запрос к БД через месяц работы:

| Показатель | Как считается | Целевое значение |
|---|---|---|
| Доля обращений через бота | заявки в БД / (заявки в БД + обращения в личку) | > 80% |
| Заявки без ручного уточнения кабинета | `room_snapshot IS NOT NULL` при создании | > 95% |
| Заявок на одно обращение | заявки / сообщения от заявителей | ≈ 1.0 (склейка работает, см. F5) |
| Закрытые заявки | `status = 'done'` / все | > 90% |
| Среднее время до взятия в работу | `avg(taken_at - created_at)` | базовая линия, цели нет |

**Вне задачи:** маршрутизация между исполнителями, SLA и эскалации, интеграция с
GLPI/Jira, база знаний, классификация обращений, автоответы. Основания — раздел 4.

## 2. Требования

### 2.1 Функциональные

| # | Требование | Проверка приёмки |
|---|---|---|
| F1 | Первое обращение незнакомого сотрудника запускает сбор профиля: кабинет, отдел | новый `telegram_id` → строка в `employees` с заполненными `room` и `department` |
| F2 | Профиль спрашивается один раз; дальше подставляется сам | второе обращение того же человека не задаёт вопросов |
| F3 | Сотрудник правит профиль командой `/profile` | `employees.room` изменился, `updated_at` обновился |
| F4 | Обращение попадает в БД и в закрытый канал одним сообщением | `tickets` +1 строка, в канале сообщение с номером |
| F5 | Подряд идущие сообщения одного человека склеиваются в одну заявку | три сообщения за 30 с → одна строка в `tickets` с тремя строками текста |
| F6 | Кнопки в канале меняют статус: `new` → `in_progress` → `done` | нажатие меняет `tickets.status` и текст сообщения в канале |
| F7 | Смена статуса уведомляет заявителя в его чат | после `done` заявителю ушло сообщение с номером заявки |
| F8 | Кнопка «Спросить» шлёт вопрос заявителю, ответ привязывается к заявке | в `ticket_messages` две строки с нужными `direction` |
| F9 | `/my` показывает сотруднику его открытые заявки | список совпадает с выборкой по `requester_id` и `status != 'done'` |
| F10 | Секреты и ПДн маскируются до записи в БД | тест: сообщение с паролем → в `tickets.text` плейсхолдер, оригинала нет нигде |
| F11 | `/stats` отдаёт исполнителю сводку за период | число заявок, среднее время до закрытия, топ заявителей |

### 2.2 Нефункциональные

| # | Требование | Значение |
|---|---|---|
| N1 | Сотрудников в контуре | 50–200 |
| N2 | Обращений в рабочий день | до 5 (~1200 в год) |
| N3 | Окно склейки сообщений в одну заявку (F5) | 45 с после последнего сообщения |
| N4 | Время от закрытия окна склейки до появления в канале | < 3 с |
| N5 | Перезапуск процесса не теряет заявки | состояние в БД, не в памяти |
| N6 | Хранилище | SQLite, файл на диске ВМ |
| N7 | Бэкап БД | ежедневная копия файла, хранить 30 дней |
| N8 | Сырой текст обращения нигде не сохраняется | ни в БД, ни в логах, ни в канале |
| N9 | Секреты бота | переменные окружения, `.env` вне репозитория |
| N10 | Рейт-лимит на сотрудника | 5 заявок в час |
| N11 | Дедупликация | одинаковый текст от одного человека за 10 мин не заводит вторую заявку |

При N2 = 5 в день объём за год — порядка 1200 строк. Это определяет почти всё
остальное: SQLite без вариантов, очередь помещается в один экран, ручные операции
исполнителя не успевают стать нагрузкой.

## 3. Модель данных

```
employees
  telegram_id         TEXT PK        -- id Telegram, не меняется
  display_name        TEXT           -- из Telegram-метаданных
  room                TEXT           -- кабинет, спрашивается один раз
  department          TEXT
  created_at          TIMESTAMP
  updated_at          TIMESTAMP

tickets
  id                  INTEGER PK     -- номер, который видит человек: «#47»
  requester_id        TEXT FK employees.telegram_id
  text                TEXT           -- замаскированный текст, склеенный из сообщений
  status              TEXT           -- new | in_progress | done | cancelled
  room_snapshot       TEXT           -- кабинет на момент заявки
  department_snapshot TEXT
  security_flag       BOOLEAN
  source_chat_id      INTEGER        -- куда отвечать заявителю
  source_message_id   INTEGER        -- первое сообщение пачки
  queue_message_id    INTEGER NULL   -- сообщение в канале, чтобы править кнопки
  text_hash           TEXT           -- для дедупликации (N11)
  created_at          TIMESTAMP
  taken_at            TIMESTAMP NULL
  closed_at           TIMESTAMP NULL

ticket_messages                      -- переписка по заявке
  id                  INTEGER PK
  ticket_id           INTEGER FK tickets.id
  direction           TEXT           -- to_requester | from_requester
  text                TEXT           -- замаскированный
  created_at          TIMESTAMP
```

**Почему `room_snapshot`, а не только `employees.room`.** Люди переезжают. Заявка
годичной давности должна помнить кабинет, в который тогда ходили, иначе отчёт по
локациям врёт задним числом.

**Почему номер заявки — автоинкремент, а не UUID.** Номер называют вслух и пишут в
переписке: «что там с 47-й». UUID для этого непригоден.

**Полей `category` и `priority` нет.** Основание — D3.

## 4. Решения и основания

Решение записано с причиной и с условием пересмотра. Без условия пересмотра решение
превращается в догму.

| # | Решение | Почему | Пересмотреть, если |
|---|---|---|---|
| D1 | Без LLM | классификация нужна для маршрутизации между исполнителями — исполнитель один; кабинет и отдел дешевле спросить один раз, чем извлекать из каждого текста. При 5 заявках в день (N2) никакая автоматизация разбора не окупается | поток вырастет до 50+ в день **и** появятся исполнители, между которыми надо распределять |
| D2 | Профиль сотрудника вместо извлечения локации из текста | кабинет не меняется от заявки к заявке — это свойство человека, а не сообщения | сотрудники перестанут быть привязаны к кабинетам |
| D3 | Категория и приоритет не хранятся вовсе | при одном исполнителе и 5 заявках в день приоритет виден глазами, а категория нужна только для отчёта, которого никто не просит | владельцу понадобится отчёт по типам проблем |
| D4 | SQLite, файл на диске | ~1200 строк в год, один процесс на запись | > 1000 сотрудников или второй пишущий процесс |
| D5 | Маскирование остаётся при любой архитектуре | пароли присылают независимо от того, есть в системе модель или нет | никогда |
| D6 | Сырой текст не сохраняется | главное требование ИБ; отдельного хранилища оригиналов нет по замыслу | явное решение владельца с описанием контроля доступа и TTL |
| D7 | Склейка сообщений по таймеру, а не кнопка «Отправить» | в личку пишут очередями: «Здравствуйте» → «принтер» → «не печатает». Кнопка требует от человека изменить привычку, таймер — нет | окажется, что люди пишут одним сообщением и таймер только добавляет задержку |
| D8 | Статусы: 4 значения | `new`, `in_progress`, `done`, `cancelled` покрывают процесс из одного исполнителя | появится второй исполнитель — понадобится `assigned` и поле исполнителя |
| D9 | Очередь в закрытом Telegram-канале, не в вебе | ноль инфраструктуры, работает с телефона, уведомления уже есть | понадобится доступ нескольким людям с разными правами |

## 5. Безопасность

- Весь текст проходит `redact()` **до** записи в БД, до отправки в канал и до логов.
  Поток односторонний и необратимый (D6).
- `security_flag: true` → заявка создаётся, сотруднику приходит предупреждение не
  присылать пароли. Заявка не отклоняется.
- Токен бота, id канала и путь к БД — переменные окружения, `.env` в `.gitignore`.
- Файл БД лежит на ВМ в контуре компании, наружу не выставляется.
- Логи пишутся через `logging`, содержат номер заявки и `telegram_id`, но не текст
  обращения.

## 6. План

Каждый этап заканчивается проверкой, которая либо проходит, либо нет. Следующий этап
не начинается, пока предыдущая не прошла.

### Этап 0 — репозиторий ✔

- [x] `git init`, `.gitignore` (`.venv`, `.env`, `*.db`, `__pycache__`), первый коммит
- [x] Проверка: `git log --oneline` показывает коммит, `git status` чист

### Этап 1 — хранилище ✔

- [x] `config.py` на `pydantic-settings`: токен бота, id канала, путь к БД
- [x] `storage/models.py` — таблицы раздела 3, SQLAlchemy 2.0 async
- [x] `storage/repo.py` — создание заявки, смена статуса, выборки для `/my`
- [x] alembic: первая миграция
- [x] Проверка: `tests/test_migrations.py` применяет миграцию на пустой БД,
      откатывает и применяет снова, и сверяет полученную схему с моделями;
      `tests/test_repo.py` заводит заявку и читает её обратно

`/stats` (F11) перенесён в этап 2: выборка зависит от того, что именно окажется
нужно в сводке, а это будет видно на живых данных.

### Этап 2 — бот

- [ ] FSM сбора профиля при первом обращении (F1, F2)
- [ ] Буфер склейки сообщений с окном N3 (F5)
- [ ] Хендлер обращения: `redact()` → запись → сообщение в канал (F4, F10)
- [ ] Callback-кнопки статусов и уведомление заявителя (F6, F7)
- [ ] Кнопка «Спросить» и привязка ответа к заявке (F8)
- [ ] `/my`, `/profile`, `/stats` (F3, F9, F11)
- [ ] Middleware: рейт-лимит и дедупликация (N10, N11)
- [ ] Проверка: каждое требование F1–F11 отмечено вручную на живом боте

### Этап 3 — пилот

- [ ] 3–5 коллег пользуются неделю
- [ ] Проверка: показатели раздела 1 посчитаны запросом к БД, склейка (F5) не рвёт
