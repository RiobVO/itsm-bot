## О проекте

Внутренний service desk на одного исполнителя. Сотрудник пишет боту в Telegram
свободным текстом — бот заводит заявку с номером, кладёт её в закрытый канал
исполнителя и держит статус, о смене которого уведомляет заявителя.

## Команды

Виртуальное окружение в `.venv` внутри проекта (Windows-раскладка путей):

```bash
.venv/Scripts/python.exe -m pytest -q              # все тесты
.venv/Scripts/python.exe -m pytest tests/test_redactor.py -v
.venv/Scripts/python.exe -m pytest tests/test_redactor.py::TestCards::test_phone_number_is_untouched
.venv/Scripts/python.exe -m pip install -e ".[dev]"
```

`pythonpath = ["src"]` прописан в `pyproject.toml`, отдельная установка пакета для
запуска тестов не нужна.

## Архитектура

Путь одного обращения:

```
Telegram → буфер склейки (45 с) → redact() → tickets в SQLite
        → карточка в канал исполнителя → кнопки статуса → уведомление заявителю
```

**Поток текста односторонний и необратимый.** `security/redactor.py` вызывается
первым, и дальше идёт только замаскированная строка: в БД, в канал, в логи. Сырой
текст живёт в памяти обработчика и нигде не сохраняется — отдельного хранилища
оригиналов нет по замыслу, а не по недоделке. Любое изменение, после которого
исходное сообщение попадает в БД или лог, ломает главное требование проекта.

**Профиль вместо разбора текста.** Кабинет и отдел — свойства сотрудника, а не
сообщения. Спрашиваются один раз при первом обращении, хранятся в `employees`,
дальше подставляются автоматически и копируются в заявку как `room_snapshot` /
`department_snapshot`. Не пытаться извлекать их из текста обращения.

**Склейка сообщений.** В личную переписку пишут очередями: «Здравствуйте» →
«у меня принтер» → «не печатает». Сообщения одного сотрудника, идущие подряд,
собираются в буфере и превращаются в одну заявку через 45 секунд после последнего.
Три сообщения = одна заявка, не три.

**Маскирование осознанно осторожно.** Ложное срабатывание уродует текст заявки, и
это дороже пропуска: стереть код ошибки или инвентарный номер хуже, чем оставить
сомнительную строку. Отсюда проверка Луна для карт, узкий список контекстов для
кодов подтверждения и различение `пароль qwerty` (маскируем) от `password reset`
(не трогаем). Негативные тесты в `tests/test_redactor.py` фиксируют эту границу —
они не менее важны позитивных.

## Закрытые решения

Подтверждены владельцем, не переспрашивать и не менять без явной просьбы. Полный
список с основаниями и условиями пересмотра — раздел 4 `TODO.md`.

- **LLM в проекте не используется.** Классификация нужна для маршрутизации между
  исполнителями, а исполнитель один; при 5 заявках в день разбор текста моделью не
  окупается. Не предлагать её обратно, пока не выполнено условие пересмотра D1.
- **Категории и приоритета нет** — ни в схеме, ни в интерфейсе. Приоритет при одном
  исполнителе и таком потоке виден глазами.
- **Секрет в тексте:** маскируем → заявку создаём → сотрудника предупреждаем,
  `security_flag: true`. Не отклоняем.
- **Статусы:** `new`, `in_progress`, `done`, `cancelled`. Поля исполнителя нет —
  он один.
- **Хранилище:** SQLite, файл на диске ВМ. Порядок величины — 1200 заявок в год.
- **Очередь** — закрытый Telegram-канал (`QUEUE_CHAT_ID`), не веб-интерфейс.
- **Хостинг:** виртуалка в облачном контуре компании. Serverless не подходит: нужен
  постоянный процесс, локальная БД и состояние буфера склейки.
