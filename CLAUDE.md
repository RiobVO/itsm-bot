# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

## О проекте

Внутренний service desk на одного исполнителя. Сотрудник пишет боту в Telegram
свободным текстом — бот заводит заявку с номером, кладёт её в закрытую группу
исполнителя и держит статус, о смене которого уведомляет заявителя.

данных, решения с основаниями и планом. Изменение поведения начинается с правки
`TODO.md`, код следует за ним. Раздел 4 `TODO.md` (решения D1–D15) содержит причину
и условие пересмотра каждого решения — прежде чем предлагать альтернативу,
проверить, не разобрана ли она там.

## Команды

Виртуальное окружение в `.venv` внутри проекта (Windows-раскладка путей):

```bash
.venv/Scripts/python.exe -m pytest -q              # все тесты
.venv/Scripts/python.exe -m pytest tests/test_redactor.py -v
.venv/Scripts/python.exe -m pytest tests/test_redactor.py::TestCards::test_phone_number_is_untouched
.venv/Scripts/python.exe -m pip install -e ".[dev]"
```

`pythonpath = ["src"]` прописан в `pyproject.toml`, отдельная установка пакета для
запуска тестов не нужна.

Миграции (путь к БД берётся из `DB_PATH`, токен бота им не нужен):

```bash
.venv/Scripts/python.exe -m alembic upgrade head
.venv/Scripts/python.exe -m alembic revision --autogenerate -m "<что меняется>"
```

Независимое ревью — Codex CLI, модель задаётся флагом:

```bash
codex exec -s read-only -c model="gpt-5.6-sol" - < review-task.txt
```

В глобальном `~/.codex/config.toml` стоит `gpt-6-astra` — владелец просил для этого
проекта `gpt-5.6-sol`, поэтому модель передаётся явно, а глобальный конфиг не трогаем.
Не добавлять в конец `| tail -N`: вывод буферизуется, и до завершения не видно ничего.

## Архитектура

Путь одного обращения:

```
Telegram → буфер склейки (45 с) → repo.create_ticket (маскирует) → tickets в SQLite
        → карточка в группу очереди → кнопки статуса → уведомление заявителю
```

**Поток текста односторонний и необратимый.** `security/redactor.py` вызывается
первым, и дальше идёт только замаскированная строка: в БД, в группу, в логи. Сырой
текст живёт в памяти обработчика и нигде не сохраняется — отдельного хранилища
оригиналов нет по замыслу, а не по недоделке. Любое изменение, после которого
исходное сообщение попадает в БД или лог, ломает главное требование проекта.

**Профиль вместо разбора текста.** Кабинет и отдел — свойства сотрудника, а не
сообщения. Спрашиваются один раз при первом обращении, хранятся в `employees`,
дальше подставляются автоматически и копируются в заявку как `room_snapshot` /
`department_snapshot`. Не пытаться извлекать их из текста обращения.

**Склейка сообщений.** В личную переписку пишут очередями: «Здравствуйте» →
«у меня принтер» → «не печатает». Сообщения одного сотрудника, идущие подряд,
собираются в буфере и превращаются в одну заявку через 45 секунд после последнего.
Три сообщения = одна заявка, не три.

**Маскирование осознанно осторожно.** Ложное срабатывание уродует текст заявки, и
это дороже пропуска: стереть код ошибки или инвентарный номер хуже, чем оставить
сомнительную строку. Отсюда проверка Луна для карт, узкий список контекстов для
кодов подтверждения и различение `пароль qwerty` (маскируем) от `password reset`
(не трогаем). Негативные тесты в `tests/test_redactor.py` фиксируют эту границу —
они не менее важны позитивных.

## Закрытые решения

Подтверждены владельцем, не переспрашивать и не менять без явной просьбы. Полный
список с основаниями и условиями пересмотра — раздел 4 `TODO.md`.

- **LLM в проекте не используется.** Классификация нужна для маршрутизации между
  исполнителями, а исполнитель один; при 5 заявках в день разбор текста моделью не
  окупается. Не предлагать её обратно, пока не выполнено условие пересмотра D1.
- **Категории и приоритета нет** — ни в схеме, ни в интерфейсе. Приоритет при одном
  исполнителе и таком потоке виден глазами.
- **Секрет в тексте:** маскируем → заявку создаём → сотрудника предупреждаем,
  `security_flag: true`. Не отклоняем.
- **Статусы:** `new`, `in_progress`, `done`, `cancelled`. Поля исполнителя нет —
  он один.
- **Хранилище:** SQLite, файл на диске ВМ. Порядок величины — 1200 заявок в год.
- **Очередь** — закрытая Telegram-группа (`QUEUE_CHAT_ID`), не веб-интерфейс. Именно
  группа, а не канал: в канале пост админа публикуется от имени канала, `from_user`
  нет и `ForceReply` не поддерживается, поэтому вопрос исполнителя не с чем связать.
  В группе он отвечает reply на карточку, и `message_id` совпадает с
  `queue_message_id`. Основание — D9.
- **Хостинг:** нужен постоянный процесс с локальным диском. Serverless (Workers,
  Vercel) не подходит и переспрашивать это не нужно: буфер склейки держит сырой текст
  45 секунд в памяти (D13), блокировка на `telegram_id` требует общего процесса,
  SQLite требует диска. Виртуалки в контуре компании **нет** — прежняя формулировка
  опиралась на неверную предпосылку. Где именно разворачивать, решается к этапу 3,
  разбор вариантов — раздел 7 `TODO.md`.

Оба этапа прошли независимое ревью (Codex, `gpt-5.6-sol`) в двух итерациях: восемь
блокирующих находок исправлены, неатомарность дедупа обоснованно перенесена в этап 2.
Разбор — в сообщениях коммитов `f9dd3b9` и `e7d52d5`.

Места, где легко наступить. Каждое найдено на живом коде, а не выписано из общих
соображений:

- **`UtcDateTime` в `models.py`.** SQLite теряет часовой пояс, и записанное
  aware-время читается наивным. Все колонки времени используют этот тип — новые
  тоже должны, иначе сравнение с `datetime.now(UTC)` упадёт в рантайме.
- **`PRAGMA foreign_keys=ON` в `session.py`.** SQLite не проверяет внешние ключи по
  умолчанию. Подключение к БД мимо `create_engine` из этого модуля отключает
  ссылочную целостность молча.
- **`render_item` в `migrations/env.py`.** Разворачивает `UtcDateTime` в `sa.DateTime`,
  чтобы готовая миграция не импортировала код приложения и применялась спустя годы.
  `render_as_batch=True` там же — без него любая правка колонки на SQLite упадёт.

- **Маскирование живёт внутри слоя хранения** — в `repo.mask()`, который зовут
  `create_ticket`, `add_message` и `find_recent_duplicate`. Сырой текст в БД — главное
  нарушение проекта, и оно не должно зависеть от памяти того, кто пишет следующий
  хендлер. **`redact()` снаружи вызывать не нужно и вредно:** текст от повторного
  прогона не меняется, а признак находки — да, второй `redact()` видит только
  плейсхолдеры и возвращает `found=False`. Поэтому `mask()` дополнительно считает
  признаком уже готовый плейсхолдер во входе, а хеш для дедупликации всегда берётся
  от замаскированного текста — иначе повтор обращения с паролем не совпал бы сам с
  собой.
- **Перечисления хранят значения, а не имена.** `_enum_column` в `models.py`
  задаёт `values_callable` — без него SQLAlchemy пишет `IN_PROGRESS`, и обещанный
  в `TODO.md` запрос `status = 'done'` не находит ничего. Новые перечисления
  заводить только через эту функцию.
- **`set_status` пишет отметки времени одним UPDATE**, а `taken_at` считает через
  `COALESCE` в самой БД. Присваивание ORM-атрибуту того же значения не помечает поле
  изменённым, и оно выпадает из UPDATE — исход тогда зависит от состояния кеша сессии.

## Проверка тестов мутацией

Тест, написанный вместе с кодом, легко зелёный не по той причине. В этом проекте так
уже было дважды: тест гонки не удерживал ссылку на объект, слабая identity map его
вытесняла, сессия перечитывала строку — и тест проходил бы на заведомо сломанной
реализации.

Поэтому тест на неочевидный инвариант проверяется мутацией: внести дефект, который
тест обязан поймать, убедиться, что он падает, откатить. Так проверены
`test_migration_matches_models` (подсаженная в модель колонка), защита
`security_flag` и очистка `closed_at`.

Откатывать мутацию точечной правкой. `git checkout -- <файл>` заблокирован хуком и
затирает рабочее дерево.

Этап 3: выбрать хостинг, автозапуск, бэкап (раздел 7 `TODO.md`), затем сам пилот.
Перед пилотом перевыпустить токен через @BotFather.

Запуск: `.venv/Scripts/python.exe -m alembic upgrade head`, затем
`.venv/Scripts/python.exe -m itsm_bot.bot`. Поля окружения — в `.env.example`.

Инварианты этапа 2, каждый найден ревью на конкретном сценарии отказа:

- **Создание заявки сериализовано на `telegram_id`.** Блокировка охватывает
  маршрутизацию, проверку дубля, рейт-лимит и `create_ticket` — иначе две
  параллельные обработки обойдут обе проверки.
- **Буфер склейки не держит блокировку во время обработки пачки.** `intake` берёт ту
  же блокировку сам, а `asyncio.Lock` не реентрантен — удержание вешает процесс.
- **Таймер буфера не отменяет сам себя.** `CancelledError` не наследуется от
  `Exception`, и самоотмена гасит пачку без следа в логах.
- **Анкета приостанавливает окно склейки и начинается с кнопки.** Без удержания
  первое обращение исчезает, пока человек отвечает; без кнопки второе сообщение
  очереди уходит в `employees.room` немаскированным.
- **Решение «ответ или новая заявка» принимается один раз на склеенную пачку.**
  На каждом сообщении оно разорвало бы ответ, написанный очередью.
- **`events_isolation=SimpleEventIsolation()` обязателен.** Без него два нажатия
  кнопок по одной заявке расходятся: в БД один статус, на карточке другой.
- **Вопрос заявителю: сначала доставка, потом запись.** И только `parse_mode=None` —
  текст человека в HTML не отправляется.
- **Кнопки анкеты не фильтруются по состоянию FSM.** `MemoryStorage` не переживает
  перезапуск, а кнопка остаётся в переписке: фильтр по состоянию делает её мёртвой,
  а нажатие без хендлера — это молчащий бот. `begin_profile` восстанавливает язык
  (из профиля, а не из локали клиента — иначе анкета перезапишет `employees.language`)
  и удержание буфера. Новую кнопку в личке заводить с тем же расчётом.
- **Ждало ли профиля обращение — знает только точка входа.** `request_possible` в
  данных FSM ставят `invite_to_profile` и `edit_profile`; по нему анкета решает,
  просить ли написать обращение заново, когда заявки из неё не вышло. Отсутствие
  профиля этим признаком быть не может — с него начинается и `/start`.
